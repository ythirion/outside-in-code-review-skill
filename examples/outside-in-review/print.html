13 Summary

Top 3 risks

  1. critical EOL runtime and vulnerable Swagger UI. netcoreapp3.1 gets no security patches and Swashbuckle 5.6.3 carries GHSA-qrmm-w75w-3wpx. A production risk as soon as the API is exposed.

Architecture

Architecture — jurassic-code

Analyzed 2026-03-09 · C4 model · Skill by Yoan Thirion

AI-inferred from code — validate with the team before sharing externally.

L1 System context

One system, three kinds of park staff, no external system. Everything (UI, API, storage) runs on the developer machine; there is no authentication.

L2 Containers

A React SPA talks to an ASP.NET Core API through the Vite dev proxy. The "database" is a dictionary held in a static field: the API and the VB.NET console client each get their own copy in their own process, nothing is shared and nothing is persisted.

L3 Components of the API

Read it from left to right: the controller depends on the service through DI, but Program also news up its own ParkService, and every instance resets the static store. Below the service, encapsulation is bypassed twice: a public static field and reflection on a private field.

L4 Code: ParkService and persistence

The domain model (Dinosaur, Zone) and the persistence model (DinosaurEntity, ZoneEntity) carry the same data under different, sometimes inverted, names. ParkService cannot be instantiated without touching the static store.

Key structural problem. Database makes _dinosaurs private, then exposes it through ReflectionHelper.GetPrivateField() (Database.cs:10). The class breaks its own contract, and ParkService goes around the data layer anyway by mutating ZoneEntity instances it reads from _db.

Assumptions

  • The three roles (operator, ranger, veterinarian) are inferred from the vocabulary of the UI and models; the code has no roles or authentication.
  • The console client is assumed to be a legacy tool kept for the workshop; nothing in the API calls it.
  • The Vite proxy target https://localhost:5001 is assumed to be the only supported way to reach the API in development.

Flow

Move a dinosaur between zones

Analyzed 2026-03-09 · UI → API → domain → in-memory store · Skill by Yoan Thirion

Why this flow

Moving a dinosaur is the only use case that crosses every layer (React form, API client, Vite proxy, controller, service, static store) and then refreshes the whole park. It runs through the main hotspot (Class1.cs) and is where the park's core safety rule, species compatibility, should apply.

Entry points: the "Move" button of DinosaurCard.tsx:52, rendered on the Dinosaurs and Zones pages · POST /Park/MoveDinosaur (ParkController.cs:58).

Sequence

Step by step

  1. UI trigger. DinosaurCard.tsx:52 calls onMove(dinosaur.name); the page stores { name, zone } in selectedDinosaur and renders MoveDinosaurForm (Dinosaurs.tsx:253).
  2. Client-side validation. MoveDinosaurForm.tsx:27 removes the current zone from the options; :36 rejects an empty destination. Closed zones are still listed.
  3. Mapping to the request. MoveDinosaurForm.tsx:40 builds MoveDinosaurRequest { fromZoneName, toZoneName, dinosaurName } from component props, no ids.
  4. HTTP call. api.ts:70 posts JSON to /api/Park/MoveDinosaur with credentials: 'include'; vite.config.ts rewrites /api and forwards to https://localhost:5001 with secure: false.
  5. Controller. ParkController.cs:58 forwards the three strings to the service; any exception becomes a 500 with the message in plain text, business errors included.
  6. Zone lookup. Class1.cs:74-84 scans the dictionary with ElementAt(i) in a for loop (quadratic) instead of TryGetValue. Source is matched by key without checking it is open; destination by key and AccessStatus == true.
  7. Mutation. Class1.cs:89-102 removes the code from the source list and adds it to the destination list, directly on ZoneEntity instances owned by the static store. The DinosaurEntity itself is untouched.
  8. Silent no-op. If the dinosaur is not in the source zone, dinosaur stays null (Class1.cs:99), nothing moves, and the API still answers 200.
  9. Refresh. After a fixed 1.5 s delay (MoveDinosaurForm.tsx:50), the page reloads the whole park with getAllZones() (Dinosaurs.tsx:74).

Risks on this flow critical

  • critical
    No compatibility check. A T-Rex can be moved into a Velociraptor or Triceratops zone; the park's main safety rule lives only on a separate "Compatibility" page.
  • critical
    Unsynchronised mutation of shared static state. Two concurrent moves can corrupt the DinosaurCodes lists.
  • warning
    False success. Moving a dinosaur that is not in the source zone returns 200.
  • warning
    Every business error is a 500. Clients cannot tell a closed zone from a crash.
  • warning
    Over-fetching after each move. The entire park is reloaded to reflect a change in two lists.

Summary

14 smells detected: 5 critical, 5 significant, 4 minor, plus 3 behaviour defects.

Recommended starting point: Global Data in DataAccessLayer.
