# Outside-In Code Review

Execute a full Outside-In Code Review on the current working directory and publish it as a
**static HTML site** in `outside-in-review/` at the root of the current directory.
Never write output files elsewhere.

`<SKILL_DIR>` below means the directory containing this `SKILL.md`.

Before starting, determine the repository name:
- Try `git remote get-url origin` and extract the repo name from the URL
- Fall back to `basename $(pwd)` if no remote is configured
- Use this name as `<REPO_NAME>` throughout all generated pages

---

## Output structure

```
outside-in-review/
├── index.html           ← dashboard + full 13-section analysis
├── architecture.html    ← C4 diagrams (Context, Container, Component, Code)
├── flow-<slug>.html     ← one business flow detailed end-to-end (sequence diagram)
├── backlog.html         ← product backlog reverse-engineered from code
├── code-quality.html    ← code smell report with letter grade
├── print.html           ← all pages assembled in one document (generated by export_pdf.py)
├── outside-in-review.pdf← the whole report as one PDF (generated by export_pdf.py)
└── assets/
    ├── report.css       ← copied from <SKILL_DIR>/assets/
    ├── diagrams.js      ← copied from <SKILL_DIR>/assets/ (renders diagrams, reports status)
    ├── vendor/          ← copied from <SKILL_DIR>/assets/vendor/ (embedded Mermaid 12.3.0, MIT)
    └── fonts/           ← copied from <SKILL_DIR>/assets/fonts/
```

Setup, before writing any page:

```bash
mkdir -p outside-in-review/assets
cp -R <SKILL_DIR>/assets/report.css <SKILL_DIR>/assets/diagrams.js <SKILL_DIR>/assets/vendor <SKILL_DIR>/assets/fonts outside-in-review/assets/
```

The site is fully self-contained: no CDN, no network access needed to read it or to validate it.
Do not modify `report.css`, `diagrams.js` or `vendor/` in the output; style everything with the classes they provide.

## HTML conventions (all pages)

Read `<SKILL_DIR>/assets/template.html` first: it is the page skeleton **and** the component catalog
(dashboard, dial, gauges, pills, signals, tables, callouts, diagram figure, backlog/smell item, numbered steps).
Copy its structure for every page; keep only the components you use.

- **Plain static HTML**, no build step, no framework. Pages must work opened directly from disk (`file://`)
  and from any static host. All links are relative.
- `<html lang="en">`, skip link, one `<h1>`, landmarks (`header`, `nav`, `main`, `footer`), `aria-labelledby` on sections.
- Same header nav on every page, with `aria-current="page"` on the current link, ending with the
  `nav__link--pdf` link to `outside-in-review.pdf` (see the template).
- Long pages (`index.html`, `backlog.html`, `code-quality.html`) use `layout layout--toc` with a sticky table of contents
  whose entries carry the section status pill.
- On pages that contain diagrams **only**, include in `<head>`, in this order:
  `<script src="assets/vendor/mermaid.min.js" defer></script>` then `<script src="assets/diagrams.js" defer></script>`.
- **Sparing emojis: none.** Status is conveyed by text pills and coloured left borders, never by emoji alone:
  - `pill--critical` / `signal--critical` — critical risk requiring immediate attention
  - `pill--warning` / `signal--warning` — notable concern to address in the short term
  - `pill--ok` / `signal--ok` — positive signal worth acknowledging
  - `pill--minor` — minor (code smells only); `pill--na` — not applicable
- **Gauges** for anything measurable: section health, coverage, mutation score, duplication, libyears,
  accessibility / eco-design conformance, smell counts. Use `.gauge` (linear, with optional `--target` tick
  for thresholds) and `.dial` (radial, for the overall score). Always set `role="meter"`, `aria-valuemin`,
  `aria-valuemax`, `aria-valuenow`, `aria-label`, and print the value as text. Colour modifier:
  `--ok` (good), `--warning`, `--critical`. When a metric is unknown, do not draw a gauge: write "not measured" with `pill--na`.
- Escape `<`, `>` and `&` in all code excerpts (`&lt;` `&gt;` `&amp;`).
- Cite locations as `<code>path/to/file.ext:line</code>`.

### Mermaid in HTML

Each diagram goes in a figure:

```html
<figure class="diagram" id="c4-container">
  <figcaption>C4 · Level 2 · Containers <span class="pill pill--na" data-render-status>rendering…</span></figcaption>
  <pre class="mermaid">
...mermaid source...
  </pre>
</figure>
```

Rules (the validator enforces them):
- The source is read as `textContent`: **escape `<` as `&lt;`, `>` as `&gt;`, `&` as `&amp;`** — e.g. `&lt;&lt;interface&gt;&gt;`,
  `--&gt;&gt;`. Never put raw tags (`<br/>`) inside a block; in labels prefer short text or `&lt;br/&gt;` (flowchart/sequence only).
- C4 diagrams use Mermaid's C4 syntax: `C4Context`, `C4Container`, `C4Component`. Element macros take quoted strings:
  `Person(alias, "Label", "Descr")`, `System(...)`, `System_Ext(...)`, `Container(alias, "Label", "Tech", "Descr")`,
  `ContainerDb(...)`, `Component(...)`, boundaries `System_Boundary(alias, "Label") { ... }` / `Container_Boundary(...)`,
  relations `Rel(from, to, "Label", "Tech")`. Every alias used in a `Rel` must be declared. No `<br>`, no unquoted commas in labels.
- The Code level uses `classDiagram`; flows use `sequenceDiagram`.
- Put assumptions as `%% ASSUMPTION: ...` comment lines (they are ignored by the renderer), and also list them in a visible callout.

## Phase 1 — Discovery Report → `index.html`

### Hero

- Eyebrow: `Outside-In Review`
- `<h1>`: `<REPO_NAME>`
- Meta line: analysis date, ~1h time-box, "Skill by Yoan Thirion" link.

### Section health score

For each section 1–12 compute a health score: start at 100, subtract 30 per critical signal and 10 per warning, floor 0.
Section status = critical if any critical signal, else warning if any warning, else ok (or n/a).
Overall health = rounded mean of applicable section scores.

### Dashboard (top of `<main>`)

1. A `card card--hero` with the overall health `.dial` (`--ok` ≥ 75, `--warning` 50–74, `--critical` < 50),
   a one-word verdict (Healthy / Needs work / At risk) and a one-sentence verdict.
2. One `a.card` per section (links to `#anchor`) with its health `.gauge` and "N critical · N warning".
3. Cards linking to the other pages with their headline figure: code quality grade (`.grade`), number of backlog
   features, C4 levels rendered (e.g. "4/4 rendered" — filled after Phase 6), and the detailed flow name.

### 01. Documentation
Read README, contributing guides, ADRs, wikis, and any available documentation.
- Is the project purpose clear?
- Can a new developer build and run the project from the README alone?
- Are setup steps, environment variables, and required services documented?

Signals:
- critical — No README or empty README
- critical — Setup steps fail or are incomplete
- warning — No architecture or decision records
- warning — Undocumented prerequisites
- ok — README is complete, setup works end-to-end

---

### 02. CI/CD Pipelines
Inspect `.github/workflows/`, `Jenkinsfile`, `.gitlab-ci.yml`, or equivalent.
- What stages are defined (build, test, lint, deploy)?
- Are there quality gates (coverage thresholds, static analysis)?
- Do pipelines run on pull requests?

Signals:
- critical — No CI/CD pipeline
- critical — Pipeline never fails despite poor quality
- warning — No coverage gate or quality threshold
- warning — PRs not gated by CI
- ok — Pipeline gates PRs with quality checks

---

### 03. Git History
Run `git log --oneline`, `git shortlog -sn`, `git log --stat` to analyze:
- Total commits and timespan
- Number of active contributors (last 6 months)
- Most changed files and their commit counts
- Commit message quality

Show contributor share as gauges (one per top contributor, % of commits).

Signals:
- critical — Single contributor on a large codebase
- critical — No commits in 6+ months
- warning — One file changed in >20% of all commits
- warning — Commit messages with no context ("fix", "wip", "update")
- ok — Healthy contributor spread and consistent commit hygiene

---

### 04. Build & Compilation
Attempt a clean build following only documented instructions.
- Does the build succeed?
- Are there undocumented steps or dependencies?
- How long does the build take?

Signals:
- critical — Build fails on clean checkout
- critical — Undocumented environment variables or services required
- warning — Build succeeds only with undocumented workarounds
- warning — No Docker Compose or dev container provided
- ok — Clean build from documented steps in under 2 minutes

---

### 05. Compilation Warnings
Read all warnings emitted during the build — do not ignore any.
- Deprecated APIs
- Security-related warnings
- Suppressed or ignored warning counts

Signals:
- critical — Deprecated APIs from 2+ major versions ago
- critical — Security-related warnings (CVE, vulnerable deps)
- warning — Hundreds of suppressed or ignored warnings
- warning — Deprecated framework features in heavy use
- ok — Clean build with zero warnings

---

### 06. Code Structure
Analyze folder hierarchy and naming before reading implementation files.
- Is there a discernible architectural pattern (layered, hexagonal, feature-based)?
- Are concerns separated (domain vs. infrastructure)?
- Is naming consistent across modules?

Show the top-level tree in a `<pre>` block (annotated).

Signals:
- critical — No discernible architectural pattern
- critical — Business logic mixed with infrastructure concerns
- warning — Inconsistent naming conventions across modules
- warning — Flat structure with hundreds of files in one folder
- ok — Clear architecture with well-named, well-bounded modules

---

### 07. Dependencies
List all major dependencies in a table: backend, frontend, external APIs, databases, message brokers.
- Are any dependencies abandoned (no releases in 3+ years)?
- Are there multiple libraries doing the same thing?

Signals:
- critical — Dependency on an abandoned library
- critical — Security-critical library with known CVE
- warning — Multiple libraries serving the same purpose
- warning — Transitive dependencies not pinned
- ok — Dependencies are maintained and well-scoped

---

### 08. Dependency Freshness
Estimate lag using LibYear (1 libyear = 1 year of version lag across all dependencies).
- Total estimated drift — gauge on a 0–15 libyears scale (value as % of 15, `--target` at 2 libyears ≈ 13)
- Security-relevant packages (auth, crypto, HTTP) specifically, in a table

Signals:
- critical — > 10 libyears total drift
- critical — Security-critical packages outdated
- warning — Some deps updated, most ignored (selective maintenance)
- ok — < 2 libyears total drift, security packages up to date

---

### 09. Quality Metrics
Use available tooling (test runners, static analyzers). Report what is available; note what is missing.
Gauges with targets:
- Code coverage % (target 80)
- Mutation score % (target 75), if configured
- Duplication % (inverse: lower is better; draw `100 - duplication` and say so in the label, target 95)
- Maximum cyclomatic complexity (table of the worst functions)

Signals:
- critical — Code coverage < 40%
- critical — Mutation score < 50%
- critical — Max cyclomatic complexity > 10 on core files
- warning — Coverage high but mutation score low
- warning — Code duplication > 5%
- ok — Coverage > 80%, mutation score > 75%, low complexity

---

### 10. Hotspots
Correlate git change frequency with complexity metrics. Hotspot = high complexity × high change rate.

Top 5 hotspot files as a table: File · Complexity · Commits (12mo) · Primary author · Risk (pill).
Identify knowledge islands (files with a single author who owns >80% of commits).

Signals:
- critical — A single file changed in >30% of all commits
- critical — Hotspot file has a single author
- warning — Hotspot files have no tests
- warning — Multiple hotspots clustered in one module
- ok — Complexity spread across many files with diverse authorship

---

### 11. Accessibility

**Language detection:** Check README, code comments, and commit messages to determine the project's primary language.
If French → apply **RGAA 4.1**. Otherwise → apply **WCAG 2.1 AA**.

**Scope detection:** If the project has no user-facing UI (pure backend, CLI, library), mark this section `pill--na` and explain why.

Analyze sources for accessibility signals (HTML templates, JSX/TSX, Vue/Svelte components, native mobile layouts):
- `lang` attribute on `<html>` element
- Semantic HTML (`<nav>`, `<main>`, `<header>`, `<button>`, etc.) vs. `<div>`/`<span>` soup
- ARIA attributes (`aria-label`, `aria-describedby`, `role`, `aria-live`, etc.)
- `alt` attributes on all `<img>` elements
- Associated `<label>` for every form input (or `aria-label`)
- Keyboard navigation: `tabindex`, focus management, no keyboard traps
- Color contrast references (CSS variables, design tokens — static analysis cannot measure rendered contrast)
- Skip links and landmark regions

RGAA-specific (if French): criteria 1.1, 8.3 / 8.4, 11.1. WCAG-specific (otherwise): 1.1.1, 1.3.1, 2.4.3, 4.1.2.
Show a conformance table (criterion · status pill · evidence) and a gauge "criteria passed / criteria checked".

Signals:
- critical — No `lang` attribute on root element
- critical — Interactive elements (`<div onClick>`) not keyboard-accessible
- critical — Images without `alt` attributes
- warning — Form inputs without labels
- warning — ARIA used incorrectly or overriding native semantics
- warning — No skip-link to main content
- ok — Semantic HTML used throughout, all images labelled, keyboard navigation intact

---

### 12. Eco-design

**Language detection:** French → apply **RGESN** (2024 edition). Otherwise → **Web Sustainability Guidelines (WSG 1.0)** / GreenIT best practices.

**Scope detection:** If the project has no user-facing digital service, mark this section `pill--na` and explain why.

Analyze:
- **Assets & payloads:** unoptimized images (no WebP/AVIF, no `srcset`, no lazy loading), autoplay/background video, fonts (count, subsetting, `font-display`)
- **Dependencies & bundle size:** production deps vs. actual usage, unused CSS, tree-shaking configuration
- **Queries & data transfers:** N+1 queries, missing pagination, over-fetching, missing HTTP caching headers
- **Rendering & computation:** polling vs. events, misplaced heavy computation, no debounce/throttle on frequent events

RGESN-specific (if French): BP 1.1, 2.6, 4.1, 6.1. WSG-specific (otherwise): 2.11, 2.15, 3.6.
Show a conformance table and a gauge "practices met / practices checked".

Signals:
- critical — Autoplay video or background animations with no user control
- critical — Entire CSS framework imported with no purge/tree-shake
- critical — No pagination on collection endpoints (potential unbounded response)
- warning — Images not converted to modern formats (WebP/AVIF)
- warning — No `Cache-Control` headers on static assets
- warning — Polling pattern where a push/event model would suffice
- warning — Unused production dependencies (> 20% of declared deps)
- ok — Assets optimized and lazy-loaded, caching in place, lean dependency tree

- **Top 3 risks** — `ol.steps`, each item starting with a critical/warning pill.
- **Top 3 questions to validate with the team** — ordered list.
- **Recommended next actions** — a 3-column table: Immediate · Short term · Medium term.
- **Detailed analysis** — `a.card` grid linking to `architecture.html`, `flow-<slug>.html`, `backlog.html`, `code-quality.html`
  with a one-line description each.

## Phase 3 — Architecture Diagrams → `architecture.html`

- Eyebrow `Architecture`, `<h1>` "Architecture — <REPO_NAME>".
- Callout: "AI-inferred from code — validate with the team before sharing externally."
- Include the two diagram scripts (`vendor/mermaid.min.js`, `diagrams.js`).

One `figure.diagram` per C4 level, each preceded by an `<h2>` and a short paragraph explaining what to read in it:

1. **Context** (`C4Context`, id `c4-context`) — the system as a black box; users and external systems. Who uses this and why?
2. **Container** (`C4Container`, id `c4-container`) — major runtime units (web app, API, DB, queue) inside a `System_Boundary`, and how they communicate (protocols on `Rel`).
3. **Component** (`C4Component`, id `c4-component`) — modules, services, controllers inside the main container (`Container_Boundary`).
4. **Code** (`classDiagram`, id `c4-code`) — classes/files of one key component; show structural issues (coupling, static state) with notes.

After the diagrams:
- "Assumptions" section: a list of every inferred user role / external system (also present as `%% ASSUMPTION:` comments in the sources).
- "Rendering check" section: a table Diagram · Type · Status (pill) filled from Phase 6 results.

## Phase 4 — Code Quality Report → `code-quality.html`

- Eyebrow `Code quality`, `<h1>` "Code quality — <REPO_NAME>".
- Dashboard: the overall `.grade` (A / B+ / C- / F; modifier `grade--a|b|c|f`), and three gauges showing the share of
  critical / significant / minor smells, plus a card "Recommended starting point".

Act as a Software Crafter Coach with 20+ years of experience in Clean Code, SOLID, DRY, Object-Oriented Design,
Functional Programming, and Design Patterns.

One `<section>` per smell family (TOC entries), each smell an `article.item`:
- `item__title`: smell name, with pill `pill--critical` (Critical), `pill--warning` (Significant) or `pill--minor` (Minor)
- `item__loc`: file / class / method / line
- 1–3 sentences of contextual explanation tied to the actual code, optionally a short excerpt in `<pre><code>`
- `<p><strong>Refactoring:</strong> …</p>` with a concrete suggestion

Priority:
- Critical — strong coupling, mutable/global data, deep nesting ≥ 4 levels
- Significant — long function, large class, duplicated code, feature envy
- Minor — mysterious name, comments, lazy element, paragraph of code

End with a summary section: "X smell(s) detected: N critical, N significant, N minor. Recommended starting point: …"

### Review protocol

**Step 1 — Global read:** understand the structure and intent before commenting.

**Step 2 — Scan by family** (full definitions in `references/catalog.md`):

1. **Readability / Naming:** Mysterious Name, Comments, Paragraph of Code
2. **Size / Complexity:** Long Function, Large Class, Long Parameter List, Deep Nesting, Bumpy Road, Loops, Variable with Long Scope
3. **Coupling / Cohesion:** Feature Envy, Insider Trading, Message Chains, Middle Man, Divergent Change, Shotgun Surgery, Alternative Classes with Different Interfaces
4. **Data Structures / Modeling:** Data Class, Data Clumps, Primitive Obsession, Global Data, Mutable Data, Temporary Field, Refused Bequest, Speculative Generality, Duplicated Code, Repeated Switches, Lazy Element

**Step 3 — Per smell:** name it → locate it → explain in context → suggest refactoring.

**Step 4 — Overall grade:** assign a letter grade (A / B+ / C- / F).

### Rules
- Never rewrite the entire code unless explicitly asked.
- Always cite the location (file / class / method / line) for each smell.
- Name the smell before explaining it.
- If the codebase is clean, say so explicitly with a `pill--ok`.
- Adapt refactoring suggestions to the language and ecosystem in use.

## Phase 5 — Detailed Flow → `flow-<slug>.html`

Always detail **exactly one** flow by default.

**Choosing the flow:**
- If `$ARGUMENTS` names a flow/feature, detail that one.
- Otherwise pick the most central business flow: the core use case of the product (the one the backlog and the
  Container diagram revolve around), preferring one that crosses the most layers (UI → API → domain → storage /
  external system) and touches a hotspot file. State in one sentence why it was chosen.
- `<slug>` = kebab-case name of the flow (e.g. `place-order`). Update the "Flow" nav link on every page to this file.

**Page content** (include the two diagram scripts):
- Eyebrow `Flow`, `<h1>` the flow name, the "why this flow" sentence, and a callout listing entry point(s).
- `figure.diagram` id `sequence` with a Mermaid `sequenceDiagram` tracing the full execution end-to-end:
  - start from the user interaction on the UI (or the external trigger: cron, message, CLI)
  - go through every component crossed, with real class/method names
  - include validations, condition checks (`alt` / `opt` blocks), mappings, persistence and external calls
  - `Note` lines for side effects and business rules
- "Step by step" section: `ol.steps`, one item per hop, each with the `<code>file:line</code>` and what happens
  (validation, mapping, storage, error path).
- "Business rules" table: Rule · Where enforced · Tested? (pill).
- "Risks on this flow" signals list (missing validation, untested branch, hotspot crossing, N+1, etc.).

## Phase 6 — Diagram Validation (mandatory, blocking)

Every report must prove its diagrams render. Run:

```bash
python3 -I <SKILL_DIR>/scripts/validate_diagrams.py outside-in-review
```

Nothing is downloaded: the script opens each page in a locally installed Chromium-based browser in headless mode
(Chrome, Chromium, Edge or Brave; set `CHROME_PATH` to force one) with the embedded Mermaid, i.e. exactly what a
reader sees. It checks, per page:
- **static** — each `<pre class="mermaid">` as the browser reads it; raw HTML tags inside a block; presence of the
  two diagram scripts;
- **render** — the `data-render="ok|error"` status that `diagrams.js` writes on every figure (with the Mermaid error message);
- **coverage** — `architecture.html` contains `C4Context`, `C4Container`, `C4Component` and `classDiagram`;
  every `flow-*.html` contains a `sequenceDiagram`.

It prints one line per diagram (`OK` / `FAIL` / `SKIP`, file:line, diagram type, error) then the other problems.
Exit code: 0 all good, 1 failure, 2 no headless browser found.

Then:
1. **Fix every `FAIL`** (escape characters, declare missing aliases, quote labels, simplify the C4 macro, add a missing
   diagram) and re-run until the script exits 0. Do not delete a diagram to make validation pass.
2. **Record the result** in the "Rendering check" table of `architecture.html` and in the dashboard card on
   `index.html` (e.g. "5/5 diagrams rendered").
3. If the script exits with code 2 (no browser), say so in both places with `pill--na` "not validated" and tell
   the user; the pages still show render errors in place when opened (handled by `diagrams.js`).

In the browser, `diagrams.js` also marks each figure caption `rendered` / `render error` and exposes `window.__diagrams`.
It also adds three buttons to every diagram caption, so readers can reuse a diagram in another tool
(mermaid.live, an IDE, a wiki): **Copy Mermaid** (source to the clipboard), **.mmd** (download the source) and
**.svg** (download the rendered image). Nothing to write for this: just keep the `figure > figcaption` structure.

## Phase 7 — PDF export

Once Phase 6 passes, export the whole report as one PDF:

```bash
python3 -I <SKILL_DIR>/scripts/export_pdf.py outside-in-review
```

The script assembles every page into `print.html` (cover with contents, then Report, Architecture, Flow, Backlog,
Code quality, each starting on a new sheet; ids are prefixed per page and links between pages become in-document
anchors, so they stay clickable in the PDF), checks that every diagram renders in it, then prints it to
